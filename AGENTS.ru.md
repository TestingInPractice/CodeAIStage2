# CodeAIStage2 — Мультиагентная система на OpenCode

## Цель
- Мультиагентная система с архитектурой на основе цикла OODA (оркестратор + субагенты)
- Корректность, поддерживаемость, тестируемость, безопасная инкрементальная поставка
- Ключевые принципы: «Простота прежде всего», «Без лени», «Минимальное влияние»

## Основные правила
1. **Минимум действий.** Делай только то, что просят. Не расширяй объём работ.
2. **Уточнение.** Если задача не до конца понятна — уточни перед выполнением.
3. **Никогда не заявляй о завершении без проверки.**
4. **Никогда не вызывай субагентов напрямую** — всегда через @orchestrator.
5. **Никогда не применяй временные исправления** — ищи первопричину.
6. **Никогда не трогай файлы вне области задачи.**

## Ожидаемая структура репозитория
- `src/`          Python-утилиты (agent_contract, context, files, metrics, reports, state, validator)
- `app/`          FastAPI-сервис
- `tests/`        pytest-тесты
- `main.py`       CLI: run / status / report --format markdown|pdf
- `tasks/` `subtasks/` `defects/` `reports/` — хранение задач и артефактов
- `.workflow/`    состояние воркфлоу (state.json)
- `docs/`         база знаний (docs/knowledge/), источники, карта проекта (docs/project-map.md)
- `.opencode/`    agents/ (оркестратор + субагенты), skills/, plugins/, opencode.json

## Операционная модель
- ВСЕ задачи проходят через @orchestrator. Всегда. Он решает, какой пайплайн
  применить, и запускает макро-OODA.
- Не вызывай субагентов напрямую и не изобретай собственный воркфлоу.
- Субагенты вызываются оркестратором; контракты — в `src/agent_contract.py`,
  детали — в `orchestrator.md`.

## Правила оркестрации воркфлоу
1. Планируй нетривиальную работу (3+ шага или архитектурные решения); при отклонении от плана — остановись и перепланируй
2. Держи основной контекст чистым — делегируй исследование/анализ субагентам (одна задача на субагента)
3. Самообучение: после каждого исправления пользователя записывай урок в `tasks/lessons.md`
   (создай файл при первой записи); просматривай уроки в начале сессии
4. Проверка перед завершением — никогда не говори «готово» без доказательств (запусти тесты, проверь логи)
5. Требуй элегантности (в меру) — элегантное решение для нетривиальных изменений;
   пропускай для простых исправлений, не переусложняй
6. Автономное исправление багов — устраняй по логам/ошибкам/упавшим тестам; не спрашивай «как»

## Управление задачами
1. Сначала план — задача в `tasks/`, состояние отслеживается в `.workflow/state.json`
2. Согласуй план с пользователем перед реализацией
3. Отслеживай прогресс (state.json обновляет оркестратор)
4. Объясняй изменения на каждом шаге
5. Документируй результаты — отчёты через `python main.py report`
6. Фиксируй уроки — `tasks/lessons.md`

## Стандарты разработки
- Аннотации типов во всех функциях; соблюдай PEP 8 (макс. длина строки 120)
- Предпочитай существующие паттерны новым абстракциям
- Не игнорируй исключения молча
- Исключения везде одинаковые и обрабатываются в одном месте
- Логирование через отдельный логгер, никогда через `print`
- При передаче между частями приложения передаётся весь объект целиком —
  все поля описаны на отдельной модели (без raw dict)
- Каждый функционал живёт в отдельной папке; новый код должен встроиться в
  проект, но при этом каждый функционал остаётся отдельным

### Принципы проектирования
- Приоритет компромиссов: Корректность > Простота > Тестируемость > Производительность > Переиспользование
- **SRP** — одна причина для изменения; если для описания нужны «и»/«или» — раздели
- **OCP** — добавляй поведение новым кодом, а не правкой существующего
- **LSP** — подклассы соблюдают контракт родителя; предпочитай композицию, когда «является» не строгое
- **ISP** — небольшие ролевые интерфейсы; завись только от используемых методов
- **DIP** — на границах завись от абстракций, а не от конкретных реализаций
- **DRY** — не дублируй логику; выноси общие правила при 3+ местах (правило трёх)
- **KISS / YAGNI** — простейшее корректное решение; никаких спекулятивных абстракций

### Архитектура и связанность
- Слабая связанность: модули взаимодействуют через контракты, а не конкретные реализации
- Разделение ответственности: разделяй домен, транспорт и персистентность;
  побочные эффекты (I/O, логирование, метрики) — на границах
- **DI** — через конструктор, а не service location; composition root — в точке входа
- **Интерфейсы / Протоколы** — для границ; не создавай пустых абстракций без ценности
- **Фабрика** — когда логика создания сложна или конкретный тип меняется
- **Композиция вместо наследования** — только когда связь по типу реальна и полезна

## Git-воркфлоу
- Conventional Commits: feat / fix / docs / refactor / test / chore
- Запускай тесты перед коммитом

## Коммуникация
- Отвечай кратко; показывай диффы изменений
- Объясняй «почему» за изменениями
- Предпочитай правку существующих файлов созданию новых
- Создавай документацию только по явному запросу

## Команды проверки
- `pytest`                              (запуск тестов)
- `python main.py status`               (состояние воркфлоу)
- `python main.py report --format markdown`   (генерация отчёта)

## Ожидаемый формат итогового ответа
1. Сводка изменений
2. Затронутые файлы/модули
3. Выполненная проверка / не проверено
4. Известные риски / тех. долг / допущения
5. Шаги ручного QA
6. Рекомендуемый следующий шаг
